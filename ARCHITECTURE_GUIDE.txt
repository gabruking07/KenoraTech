KenoraTech Architecture Guide

Purpose

KenoraTech is currently one Next.js application. It has both the public/admin frontend and secure backend API routes in one repository.

This is intentional: Vercel supports Next.js frontend pages and app/api backend routes in the same deployment. There is no separate Express server to run or deploy. The website is still logically separated into frontend, backend, data, and assets through folders.


Main Structure

app/
Frontend routes and server API routes.

app/page.tsx
The public homepage route.

app/about/, app/services/, app/portfolio/, app/pricing/, app/contact/, app/careers/, app/process/
Public website pages. Each folder contains a page.tsx file for its URL.

app/admin/
Authenticated admin dashboard routes. These routes use the existing AdminAuthGate and admin layout.

app/api/
Backend API routes. These run securely on the server when deployed to Vercel. Browser code calls these endpoints using fetch().

Important API groups:
- app/api/admin/: protected admin-only APIs, including content and analytics reads.
- app/api/analytics/track/: public write-only endpoint for anonymous visitor tracking.
- app/api/contact/: contact-form APIs.
- app/api/portfolio/: portfolio CRUD APIs.
- app/api/jobs/ and app/api/applications/: careers and application APIs.

Why app/api is used instead of a separate server folder:
- Vercel deploys it with the website automatically.
- The frontend and backend share TypeScript types and validation helpers.
- No second deployment URL, server process, or CORS configuration is required.
- Admin authentication and MongoDB secrets remain server-side.


components/
Reusable frontend UI. Components should not directly connect to MongoDB or expose secrets.

components/layout/
Header and footer used by the regular public website.

components/sections/
Reusable public website sections, such as Services and Team.

components/admin/
Admin dashboard UI only: sidebar, dashboard cards, managers, tables, forms, and AnalyticsPanel.

components/analytics-tracker.tsx
Invisible public browser component. It sends anonymous page-view and heartbeat events to /api/analytics/track. It does not render a public dashboard or analytics content.

components/app-shell.tsx
Public website shell. Controls the temporary LAUNCH_MODE switch, header/footer, background, and public analytics tracker.

components/ui/
Small generic interface primitives such as buttons and cards.


lib/
Server-safe shared logic, database access, validation, and reusable data helpers.

lib/mongodb.ts
Creates and reuses the MongoDB connection. Only server code should use it.

lib/admin-auth.ts
Checks the ADMIN_TOKEN sent by the authenticated admin dashboard.

lib/analytics.ts
Analytics source classification, MongoDB collection access, and database index setup.

lib/portfolio.ts, lib/jobs.ts, lib/contact-submissions.ts, lib/applications.ts
Database models/helpers for their respective data types.

lib/content.ts
Existing shared static website content. CMS-managed content should gradually be moved to database/API-backed collections where applicable.


data/
Temporary/static data used by the current admin dashboard presentation. It is not the MongoDB database.

data/admin/
Dashboard sample/display data and types. Live CMS or analytics data should come from app/api endpoints instead.


public/
Static files served directly by the website.

Examples:
- public/kenora-tech-logo.png: official logo.
- public/portfolio/: portfolio thumbnail assets.
- public/robots.txt and public/sitemap.xml: SEO files.

Use public/ for files that should be accessible by URL. Do not store secrets here.


assets/
Source image assets imported into React/Next components at build time, such as homepage artwork and page illustrations.


Database

MongoDB Atlas is the only database. Its connection is configured through MONGODB_URI (and optionally MONGODB_DB) in .env.local locally and Vercel environment variables in production.

MongoDB collections currently include content, portfolio, contact, jobs, applications, and analytics collections.

Analytics collections:
- analyticsSessions: anonymous active session state and last-seen timestamp.
- analyticsPageViews: anonymous page-view events used for historical reports.

Do not put database credentials in components/, public/, assets/, or client-side variables.


Environment and Configuration Files

.env.local
Local secrets such as MONGODB_URI, MONGODB_DB, ADMIN_TOKEN, and Cloudinary credentials. Never commit this file.

.env.example
Safe example environment variables. Update this when a new required variable is added.

package.json
Project dependencies and commands.

next.config.ts, tsconfig.json, tailwind.config.ts, postcss.config.mjs, eslint.config.mjs
Next.js, TypeScript, Tailwind, PostCSS, and lint configuration.


Generated Folders (do not edit)

node_modules/
Installed packages.

.next/
Generated Next.js development/production output.

tsconfig.tsbuildinfo
Generated TypeScript cache.


How Requests Flow

Public page or admin UI
        |
        v
React component in components/ or route in app/
        |
        v
fetch() to app/api/... when live data is needed
        |
        v
Server route validates request and checks ADMIN_TOKEN if required
        |
        v
lib/ helper connects to MongoDB
        |
        v
MongoDB Atlas


Why This Is Better Than client/ and server/ Folders Right Now

Creating a separate client/ and server/ application would require:
- A new Node/Express/Fastify backend setup.
- A separate Render, Railway, VPS, or serverless API deployment.
- CORS configuration between the frontend and backend.
- Separate environment-variable configuration and deployment monitoring.
- Updating Vercel configuration because it would no longer run the API routes directly.

The current Next.js arrangement already keeps responsibilities separate while avoiding those deployment costs and risks. If the project later needs a dedicated external API for mobile apps or many services, it can then be extracted into a real server/ application safely.
